## A. NLI 모델 관련 질문 (가장 가능성 높음)

### Q. NLI 모델로 왜 다국어 MiniLMv2를 선택했나요? 한국어 특화 모델이 있을 텐데?

**답변**:
세 가지 이유로 `MoritzLaurer/multilingual-MiniLMv2-L6-mnli-xnli`를 선택했습니다.

1. **검증된 NLI 작업**: XNLI 데이터셋은 한국어를 포함한 15개 언어에 대한 NLI 표준 벤치마크입니다. 모델이 이미 한국어 NLI 작업에 fine-tune 되어 있어 추가 학습 없이 사용 가능합니다.

2. **경량성**: 약 110MB로 Worker 컨테이너 부담이 적습니다. 한국어 특화 BERT 계열 모델(KLUE-BERT 등)은 400MB 이상이라 분산 처리 환경에서 메모리 부담이 큽니다.

3. **다국어 확장성**: 향후 영문 기사 분석 등 다국어 지원으로 확장할 때 모델을 바꿀 필요가 없습니다.

다만 한국어 특화 모델로의 교체 가능성도 열어두었습니다. 향후 KLUE-NLI 같은 한국어 전용 NLI 모델로 비교 실험(Ablation Study)을 진행할 예정입니다.

### Q. NLI 60%, 코사인 20%, 키워드 20%의 가중치 근거는?

**답변**:
이 비율은 단일 논문에서 도출된 수치가 아닌 **다중 신호 앙상블의 설계 결정**입니다. 근거:

1. **NLI를 메인 신호로**: Bowman et al. 2015 [4] 이후 NLI는 의미 함의 판정의 표준 작업으로 자리 잡았습니다. 본 작업의 핵심 신호이므로 60% 부여.

2. **어휘 신호로 견고성 보강**: NLI 모델 단독 의존은 모델의 분포 외 데이터에서 불안정할 수 있어, 검증된 어휘 신호(TF-IDF 코사인)와 키워드 매칭을 각 20%로 결합했습니다. 모델 hallucination이나 분포 외 데이터 영향을 분산.

3. **합계 80% (어휘) : 20% (모델)는 학계 흐름과 일치**: Horne & Adali 2017 [5] 등에서 어휘 기반 특징이 가짜뉴스 판별에 강한 신호임이 입증.

향후 라벨링 데이터를 활용한 가중치 데이터 기반 최적화도 가능합니다.

### Q. 본문 일치도 점수 1.3점은 너무 낮은 거 아닌가요?

**답변**:
이건 의도된 동작입니다. NLI 모델이 "제목과 본문이 의미적으로 완전히 모순됨"으로 판정했을 때, entailment 확률이 1% 미만이고 contradiction이 90% 이상이라는 의미입니다. 점수 산식이 `entailment×100 + neutral×50 + contradiction×0` 이므로, 모순이 강할수록 0에 수렴합니다.

평가 데이터셋의 mismatch 케이스에서 본문일치도가 1.3 / 19.8 / 6.1점으로 측정된 것은 **제목과 본문이 완전히 다른 주제임을 시스템이 정확히 인식**한 결과입니다.

이게 본 시스템의 차별점 — 기존 어휘 기반 분석으로는 모호하게 50~60점이 나올 케이스를, NLI로 명확히 분리합니다.

## B. 캐싱 관련 질문

### Q. LRU 캐시가 진짜 성능 향상에 도움이 되나요? 실측 데이터 있나요?

**답변**:
네, 실측했습니다. 같은 본문이 반복 입력될 때(예: 동일 도메인의 비슷한 기사):
- **캐시 미스 (첫 분석)**: 1.5초
- **캐시 히트 (재분석)**: 0.22초
- **단축률**: 약 7배

캐시는 3종:
1. NLI 추론 (premise + hypothesis 해시 키)
2. KR-FinBert 감성 추론 (본문 리드 해시 키)
3. 출처 분류 (도메인 키)

이 중 출처 분류는 도메인 단위라 적중률이 가장 높고, NLI/감성은 본문 내용이 같아야 적중합니다. 실서비스에서는 같은 도메인의 비슷한 보도가 자주 들어와 NLI 적중률도 30~40% 정도 기대됩니다.

### Q. 캐시가 분산 환경에서 일관성 문제는?

**답변**:
현재 LRU 캐시는 Worker 컨테이너별 로컬 메모리라 컨테이너 간 공유는 없습니다. 이는 **의도된 설계 결정**입니다:

1. **단순성**: Redis 등 외부 캐시 도입 시 추가 인프라 복잡도
2. **충분한 효과**: 같은 URL은 RabbitMQ가 한 Worker에 분배하므로 컨테이너 내 적중률만으로도 충분
3. **확장성**: Worker 추가 시 캐시도 자동 분산

향후 Worker가 수십 개로 늘어나면 Redis 공유 캐시로 전환 가능합니다.

## C. 분산 처리 관련 질문

### Q. Docker 컨테이너 3개를 한 호스트에서 돌리는 게 진짜 분산인가요?

**답변**:
"분산 처리"의 정의에 따라 답이 달라집니다. 본 시스템은 **분산 처리 패턴의 핵심 3요건**을 충족합니다:

1. **장애 허용**: `auto_ack=False`로 Worker 크래시 시 RabbitMQ가 메시지를 다른 Worker에 자동 재분배.
2. **부하 분산**: `prefetch_count=1` + 라운드로빈으로 Worker 간 균등 분배.
3. **수평 확장**: `docker compose up --scale worker=N`으로 Worker 수 즉시 증감.

각 Worker는 독립된 컨테이너로 자체 hostname, 자체 메모리 공간을 갖습니다 (예: `effb94e95ee4`, `618b32523f51`, `9f33a765a99c`). 이는 분산 시스템의 기본 단위인 "독립된 실행 환경"을 만족합니다.

물리적 다중 호스트가 아닌 이유는 학회 발표/시연 환경의 제약이며, 동일한 코드를 Kubernetes 등 다중 호스트 환경에 배포 시 코드 수정 없이 동작합니다. 메시지 큐 기반 비동기 분산 패턴의 핵심은 호스트 수가 아닌 **느슨한 결합과 수평 확장 가능성**입니다.

### Q. RabbitMQ가 SPOF (단일 장애점) 아닌가요?

**답변**:
맞습니다. 현재 RabbitMQ는 단일 인스턴스라 이게 죽으면 시스템 전체가 멈춥니다. 운영 환경 확장 시 다음 옵션이 있습니다:

1. **RabbitMQ Mirror Queue**: 클러스터링으로 큐를 여러 노드에 미러링
2. **Quorum Queue**: Raft 기반 합의 알고리즘으로 고가용성
3. **외부 메시지 큐**: AWS SQS, Google Pub/Sub 등 매니지드 서비스

본 시스템은 학회 발표 + 프로토타입 단계라 단일 인스턴스로 구현했고, 실서비스 단계에서는 위 옵션 중 하나를 도입할 계획입니다.

### Q. Worker 늘리면 진짜 빨라져요? Amdahl's Law는?

**답변**:
실측 결과:
- Worker 1개로 20건 처리: 12.2초
- Worker 2개로 20건 처리: 10.2초 (17% 단축)
- Worker 3개로 20건 처리: 10.1초

Worker 2→3에서 큰 차이가 없는 이유는 Amdahl's Law대로 **직렬 부분(SQLite 쓰기 경합, RabbitMQ 큐 라운드트립)이 병목**이 되기 때문입니다. 측정 단위가 20건으로 작아서 모델 로딩 오버헤드도 영향이 큽니다.

이 한계를 해결하려면:
1. SQLite → PostgreSQL 이전 (동시 쓰기 가능)
2. 캐시 적중률 향상으로 추론 시간 단축
3. 더 큰 데이터셋(200건 이상)에서 측정해 Worker 확장 효과 명확화

본 시스템은 메시지 큐 기반 패턴의 정당성을 입증했고, 병목 분석과 향후 개선 방향까지 명확히 제시했습니다.

## D. 보안 / 운영 관련 질문

### Q. 사용자 비밀번호는 어떻게 저장하나요?

**답변**:
bcrypt로 해싱하여 저장합니다. 평문은 절대 저장하지 않으며, salt는 bcrypt가 자동으로 사용자별로 생성합니다. 또한:

- 비밀번호 강도 검증: 영문+숫자 모두 포함 8자 이상
- 세션 토큰: `secrets.token_hex(32)`로 256비트 랜덤
- 토큰 만료: 7일 후 자동 무효화
- 비밀번호 변경 시 모든 기존 세션 무효화 (다른 디바이스 자동 로그아웃)

### Q. 분석 결과를 다른 사용자가 볼 수 있나요?

**답변**:
**아니요. 완전히 격리됩니다.**

- 모든 `analysis_results`와 `jobs` 테이블에 `user_id` 외래키
- API 모든 endpoint에 `auth_user(request)` 미들웨어 적용 — 본인 데이터만 SQL WHERE 절로 필터
- 다른 사용자의 결과 ID로 직접 GET 시 HTTP 403 반환
- 검증 실험: alice와 bob 회원으로 각각 분석 시 결과 겹침 0건 (Phase G 작업 시 실측)

공유 링크 기능은 명시적으로 본인이 "공유 발급" 버튼을 눌렀을 때만 활성화되며, 그 경우에도 `user_id`와 일부 메타데이터는 마스킹됩니다.

### Q. 운영 환경에서 어떻게 배포하나요?

**답변**:
세 가지 옵션을 준비했습니다:

1. **로컬 단일 호스트** (학회 발표 용): `docker compose up -d` 한 줄.
2. **외부 인터넷 노출** (시연용): ngrok 터널 통합. `.env`에 NGROK_AUTHTOKEN 입력 후 `--profile tunnel up -d` 하면 HTTPS URL 자동 발급.
3. **CI/CD 자동 배포**: GitHub Actions가 main 푸시 시 GHCR(GitHub Container Registry)에 이미지 자동 빌드/푸시. 팀원은 `docker compose -f docker-compose.prod.yml pull && up -d` 두 줄로 즉시 가동.

## E. 알고리즘 / 평가 관련 깊은 질문

### Q. Accuracy 66.7%면 낮은 것 아닌가요?

**답변**:
Strict Accuracy 66.7%이지만 **Loose Accuracy 100%**로 더 의미 있게 봐야 합니다.

본 시스템의 등급 분류는 0~100점 연속 점수를 4등급으로 이산화한 결과이므로, 등급 임계치(80/60/40)에 점수가 가까운 경계선 케이스가 인접 등급으로 분류되는 것은 자연스럽습니다. **결정적 오류(정상→의심 또는 의심→정상 같은 등급 2단계 이상 차이)는 0건**으로, 시스템 판단을 사용자가 신뢰하고 참고할 수 있는 수준입니다.

또한 평가 데이터셋이 12건 합성 데이터로 통계적 무게가 제한적입니다. 향후 SNU 팩트체크 또는 KFND 같은 공개 가짜뉴스 데이터셋으로 대규모 평가가 필요합니다.

### Q. 자극성 단어 사전이 객관적인가요? 누가 정했나요?

**답변**:
사전은 4 카테고리(과장/혐오/선정/공포)로 총 ~80개 단어를 팀에서 큐레이션했습니다. 출처:

- Alonso et al. 2021 [6]의 감성 분석 결과를 참조한 단어 카테고리
- 한국어 가짜뉴스 사례 분석 (낚시성 제목 패턴 수집)
- 학계 가이드라인 (혐오 표현 등)

다만 사전 단독 의존은 위험하므로 KR-FinBert-SC 감성 모델과 50:50으로 결합해 단어 한정성 극복.

또한 사용자가 본인 기준으로 사전을 추가/제외할 수 있는 사용자화 기능도 구현되어 있습니다 (E3 — 사용자 자극성 사전).

### Q. 출처 신뢰도 매체 사전은 어떻게 정했나요?

**답변**:
한국 언론계의 일반 인식과 학술 자료 기반:

- **주요 언론사 (85점)**: 통신사(연합) + 지상파(KBS/MBC/SBS) + 종합일간지(조선/중앙/동아/한겨레 등) + 종합편성채널(JTBC/TV조선 등) 약 25개.
- **등록 인터넷 매체 (65점)**: 인터넷 신문(뉴시스/뉴스1/오마이뉴스 등) + 경제지(매경/한경/서경 등) + IT/전문지 약 50개.
- **출처 불명 (35점)**: 위에 매칭되지 않은 모든 매체.

이 분류는 절대적 신뢰도가 아닌 **상대적 가중치**이며, 출처는 보조 지표(20%)로만 사용. 향후 한국언론진흥재단의 매체 등록 데이터베이스와 연동하여 약 600개 정식 등록 매체를 자동 분류하는 방향으로 확장 가능합니다.

## F. 향후 확장 / 한계 관련

### Q. 본 시스템의 한계는 무엇입니까?

**답변** (논문 결론과 동일 톤):
다음 한계를 인식하고 있습니다.

1. **3가지 지표 한계**: 본문일치/자극성/출처만으로는 변형되는 가짜뉴스 패턴을 모두 잡기 어려움. 외부 지식 기반 팩트체크와 결합 시 정확도 향상 기대.

2. **데이터 기반 가중치 부재**: 현재 45/35/20은 학술 근거 기반 초기값으로, 라벨링 데이터를 활용한 데이터 기반 최적화 여지가 있음.

3. **단일 호스트 분산**: 메시지 큐 패턴은 다중 호스트 확장 가능성을 입증했으나 본 평가는 단일 호스트 내 컨테이너 분산에 한정.

4. **합성 평가 데이터셋**: 12건 합성 데이터로 통계적 무게 제한. 공개 가짜뉴스 데이터셋과의 연동 평가 필요.

향후 연구 방향:
- 새로운 평가 지표 도입 (사실관계 검증, 문체 분석 등)
- 데이터 기반 가중치 최적화 (강화학습 또는 베이지안 최적화)
- 외부 팩트체크 시스템 연동 (SNU 팩트체크, Google Fact Check API)
- 다국어 지원으로 영문 가짜뉴스 검출

## G. 발표 중간에 막혔을 때 — 안전 답변 템플릿

심사위원이 예상 외 질문을 했을 때 사용 가능한 일반 답변:

> **"좋은 지적입니다. 본 시스템은 학회 발표/프로토타입 단계로 그 부분은 현재 [기본/한정]으로 구현되어 있으며, 실서비스 단계에서는 [언급한 방향]으로 확장 가능하다고 판단합니다. 구체적인 구현은 향후 연구로 진행할 예정입니다."**

핵심: 한계를 인정하되 확장 가능성을 제시. 솔직함이 학술 발표의 기본 덕목.

| **66.7% / 100%** | Strict / Loose Accuracy |
